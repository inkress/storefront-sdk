## What the SDK already has (read 2026-09-20, cite src/…)
- HttpClient (`src/client.ts`): base `https://api.inkress.com/api/v1`; auth = `Authorization: Bearer <token>` + `Client-Id: m-<username>`; envelope `ApiResponse = {state:'ok'|'error', data?, result?}`; 30s timeout, 5xx/timeout retries.
- Resources: merchants, products, categories, auth, orders, cart, wishlist, generic, generics, reviews, shipping, files, checkout, addresses.
- Checkout (`src/resources/checkout.ts`): `createPaymentUrl()` (hosted-order URL, base64 `order_token` → `/merchants/:username/order`); `createSession()`→`POST /checkout/sessions` (PowerTranz SPI, returns `frame_url`/`spi_token`/`redirect_data`); `getSession`/`cancelSession`; `redirectToCheckout`.
- Checkout types (`src/types/checkout.ts`): `CheckoutSessionFees` == the commerce-web `/fees` breakdown (sub_total, discount_total, tax_total, customer_total, fee_mappings, …). Session input has NO `discount_code`.
- Cart (`src/resources/cart.ts`): local (localStorage) + remote `/carts`; events (`cart:item:added` …); `buildCheckoutInput()`→session. Remote `CartLineItem` has `variant_id` but LOCAL cart fakes it (`cart.ts:351 variant_id: item.product.id // TODO`).
- Variant/stock/facet helpers (`src/utils/variants.ts`): product custom-fields/options (marketplace model), stock (`unlimited`/`units_remaining`), facet rows. NOT a variant entity.
- Payment helpers (`src/utils/payment.ts`): base64 order-token URL builder (major units).
- Query system shared with admin-sdk; 97 tests; design spec `docs/superpowers/specs/2026-08-09-…addresses-variants-stock-facets-design.md`.

## Confirmed SDK-side gaps (nameable now)
1. **No first-class Variant entity.** Cart keys by `product.id` (`cart.ts:178`) so it can't hold two variants of one product; `syncToRemote` fakes `variant_id = product.id` (`cart.ts:351`); `buildCheckoutInput` sends `{id: product.id, quantity}` (`cart.ts:139`) — no variant id. FleekSite non-negotiable: a buyable card needs a variant. **(Biggest gap; blocked on Agent A's backend variant contract.)**
2. **Checkout money-path is session-only.** `createSession`→`/checkout/sessions` has no `discount_code` in its input; the LIVE commerce-web `/checkouts/:id` uses the order-first processor path (top-level `discount_code`) which DOES apply discounts. Peer reports session-based drops discounts (discount_total=0). **The SDK must expose whatever path keeps discounts. (Blocked on Agent B verdict.)**
3. **Auth gaps.** No `GET /auth/me` (only `getProfile(id)` + `validateToken()→bool`); no email-code login (`/auth/login/code` → `/auth/login/verify`). Path names (`/auth/request_reset`,`/auth/reset`) differ from FleekSite's (`/auth/reset-password`…) — reconcile once Agent C says whether fs-hono auth is Inkress-backed or a separate site-scoped users table.
4. **No bulk stock check.** `products.checkStock(id)` re-fetches one product; FleekSite needs `POST /variants/check_stock {variant_ids:[]}` → `[{id,stock}]`.
5. **Envelope normalization.** Inkress endpoints are inconsistent (`data` vs `result`); the FleekSite kit + hooks read `{state, data}`. The SDK's kit layer must present a single `{state,data}` shape.
6. **No live-search shape.** FleekSite `GET /search.json?q=` → `{products:[{title,url,image,price,label,available}], pages:[…]}` (built on variants). No SDK equivalent.
7. **No leads resource.** `POST /api/v1/leads {name,email,phone,body,data}` (contact/newsletter). Absent.
8. **Kit not in the SDK (Romario's steer).** `pipeline/kit/core/fk.js` + `fk-cart.js` (data-fk-* hooks, `fk:cart`/`window.fkCart`, behaviour suites) live in FleekSite. Phase ④ ports them into the SDK with PARITY (hooks + `{state,data}` + suites preserved).
9. **NOT published to npm.** `latest = 0.0.1` stub (HANDOVER.md); 1.1.2 built/tagged/merged but unpublished (blocked on Romario's npm 2FA OTP). Blocks commerce-web consuming it via `npm install` (Phase ②). Interim: install from git, or Romario publishes. **Surface to Romario.**
10. **Render-time out of scope under A-sync.** `{% collection %}` stays local-DB Liquid; the SDK need not serve render-time.

## FleekSite kit delivery constraints (Phase ④ — from the kit-authoring session, 2026-09-20)
Five facts that constrain the port (2 are hard constraints, not preferences):
1. **fk.js/fk-cart.js are site TEMPLATES today, not a library.** `build.py` writes each as a template row (type 9) served from the site's own origin `/js/fk.js`,`/js/fk-cart.js`, cache-busted `?v=<build>`. A kit change reaches every site on next build, unversioned. SDK-as-package inverts this: each site pins a version; "fix everywhere" becomes "rebuild N sites." Deliberate operational change — decide with Romario.
2. **SAME-ORIGIN IS LOAD-BEARING (hard).** Every kit call is `credentials:'same-origin'` to the site's own host; the session is an httpOnly `current_user` cookie. Script origin (CDN) is fine, but if a *call* moves to an Inkress host the cookie stops travelling → auth/cart/checkout break. **Insight/resolution:** the SDK gets TWO transport modes — (a) direct-to-Inkress with `Bearer` token (commerce-web `/checkouts/:id`, first-party apps; current HttpClient) and (b) **same-origin cookie mode** (relative base, `credentials:'same-origin'`, no Bearer) for FleekSite storefronts, where the kit calls the site's own fs-hono routes and fs-hono delegates to Inkress server-side. This means "Inkress backs fs-hono's REST server-side" is FORCED for the browser calls (unless we move FleekSite auth to tokens) — it's not a duplication, it's the transport boundary. The SDK owns the JS kit; the same-origin REST stays same-origin. **Client work: add a cookie/same-origin transport mode to HttpClient.**
3. **No build step, on purpose.** ES5 IIFEs, no modules/bundler, run as plain `<script defer>`. SDK ships ESM/TS → FleekSite needs a built UMD/IIFE artifact. The SDK already emits `dist/index.browser.js` (browser global via rollup) — ship a no-build IIFE kit bundle; don't assume the consumer bundles.
4. **Config comes from the DOM (good news).** `commerce/head.liquid` sets `<html>` attrs at render: `data-site`,`data-currency`,`data-signed-in`,`data-cart-style`,`data-money-style`,`data-currency-symbol`; live rates rendered as JSON in `#fk-rates`, applied client-side (page stays cacheable). The SDK kit must read config from the host document (same seam), NOT require an `init()` call the templates would have to add.
5. **Cart shape is a SERVER contract.** Platform doesn't model a cart: `POST /api/v1/cart` stores opaque `info` jsonb; line management is the client's job. fs-hono `CheckoutService` parses `info.items[] = {variant_id, post_id, price, quantity, total, title}` and computes Σ price×quantity. Item shape + units are load-bearing server-side. (Server still re-prices/re-resolves per §3 non-negotiables — confirm with Agent C how CheckoutService reconciles posted price vs DB price.)
6. **Service-worker cache trap (hard).** Every storefront registers a Workbox SW: `registerRoute(/.*\.(?:js|css)/, staleWhileRevalidate({cacheName:'static-cache', expiration:{maxEntries:50, maxAgeSeconds:7d}}))` — ANY `.js`/`.css` is served cache-first, background-refreshed, 1-week ceiling. Today the build's per-build `?v=<build>` query defeats it (new cache key each build). If the SDK bundle loads from a STABLE URL (CDN path, or unversioned `/js/inkress-storefront.js`), a returning visitor runs the OLD bundle for ≥1 page load after an upgrade — up to a week — a ghost "fix isn't live for some customers", worst exactly while cart/checkout behaviour is changing. **Fix: put a version/hash IN THE URL** (`…@1.4.2/dist/index.browser.js`, or keep the template's `?v=`), or have the SW skip the SDK path (former is less work, no platform change). Same for the kit's CSS if it moves with it.
- **Regression gate reality:** the two behaviour suites run against LIVE SITES over HTTP (origin + `work/fixtures.mjs` per-site facts), not a component harness, and they block service workers (the platform injects one for navigations). So "both ports pass" needs a real site SERVING the SDK build — stand that environment up EARLY in Phase ④, not at the end.
- **Ownership:** the kit-authoring session (authored STOREFRONT-SDK-REQUIREMENTS.md) is PAUSED; consult it on the parity contract only if Romario reactivates it. The active [77c89d] session owns the templates and has migrated both ports onto dedicated per-theme sites — get CURRENT hosts from it, not from any HANDOVER.

## Discount contract — CONFIRMED (discounts session, 2026-09-20) + folded into the SDK
Authoritative answers from the discount-owning session; the SDK's discount surface now reflects them (107 tests green):
- **Reject `reason` enum (8, `Service.Discount`):** `not_found`, `inactive`, `expired`, `usage_limit_reached`, `per_customer_limit_reached`, `not_valid_for_items`, `currency_mismatch`, `min_spend_not_met`. → typed as `DiscountRejectReason`; `DiscountQuote.reason` uses it. (`min_spend_not_met` slug is fixed; the human `message` carries the amount.) **Currency (commerce-api #217):** a fixed code CONVERTS to the order currency (percentage codes are currency-agnostic); `currency_mismatch` now means "no exchange rate / unsupported currency" only, not code-vs-order.
- **Scoped quote `products:[{id,cost}]`:** `id` = product id (== `variant_id` today; send the line's `variant_id`, what order_lines freezes + eligibility matches). `cost` = per-LINE total (qty already in) — invoice line = `product_variant_total_frozen`, cart line = unit_price×qty. Quantity NOT sent separately. → `DiscountLineInput{id,cost}`; `validateDiscount` POSTs when `products` present (a products[] can't be querystring-encoded), GETs otherwise.
- **Combinability:** ONE code per order, no stacking; applied as a single "discount" fee group (payer = merchant, BEFORE tax), coexisting with tax/shipping/platform/provider groups.
- **Currency:** gated by the CODE's `currency_code` (same rule both units): set → valid only when cart currency matches, else `currency_mismatch`; null/"" → any currency. (Convention only: fixed usually set, % usually null.)
- **Quote is ADVISORY:** order-create RE-RESOLVES + RE-CHECKS under a `FOR UPDATE` lock (usage_limit + per_customer_limit from live counts) → a green-quoted code can still be refused at `POST /orders` if a cap fills in between. `/fees` is LENIENT (bad code → discount 0, no reject); use `/discount` for the reason. → documented on `validateDiscount` + `createOrder`; the app must surface the order-create rejection.
- **Client NEVER:** send a price/discount amount (server prices); send `unit`/`applies_to` as strings (INTEGER enums 1/2 — the #197 bug); send `usage_count` (derived/read-only). (The last two bind the ADMIN CRUD path, which lives in commerce-web's dashboard via admin-sdk, not this storefront SDK.)
