# PARITY-payments — session-based vs order-first payment mechanics (commerce-api, READ-ONLY audit 2026-09-21)

Scope note: audit repo is `commerce-api` (canonical, not worktrees). The order-first "mature reference" is the CDE / commerce-payments forced-3DS charge flow in `fac.ex` + `payment_link_controller.ex`. The **inbound** FAC webhook processor and the **FAC settlement reconciler** (`CaptureFlipReconciler`, `mix payments.reconcile_fac`, rpTransaction matching) live in the sibling **commerce-worker** repo — confirmed absent from `commerce-api/lib` — so where those bear on a dimension they are marked `[commerce-worker, out-of-repo]`. Key money identifier for both refunds and reconciliation is `ledger_transactions.payment_method_order_id`: `update_status/2` keys on it (`lib/api/context/payment/transactions.ex:29-40`); `retrieve_payment_method_id/retrieve_transaction_id` key on it (`lib/api/services/payments/providers/utils.ex:75,91`).

Routing correction (verified, NOT a gap): `Fac.detect_session_webhook` in `commerce-api/lib/api/services/payments/providers/fac/fac.ex:357-381` only recognises `sess_`/`fac_session_`/`|` and would misroute the `O.x.S.x` session id — but that copy is NOT on the inbound path. Inbound FAC webhooks enter via `payment_controller.ex:140` → `Workers.Orders.Fac.WebhookProcessor` `[commerce-worker]`, whose `detect_session_webhook` DOES match `O.XXXXXXXX.S.xxxxxxxxxxxx` and routes to `FacSessionWebhookWorker` → `SessionBasedCheckout.handle_payment_webhook`. So session webhooks reach the session handler in production.

### 1. 3DS / SCA (frictionless, challenge, step-up, complete-3ds, retry, decline outcome)
- order-first: Full in-band challenge loop. `checkout_intent` (fac.ex:878) issues a signed amount; `generate_charge`/`charge_card_ref` sends `three_d_secure: true` (fac.ex:563,957-974); a challenge returns `transaction_stage: "challenge"` + `redirect_data`/`spi_token` (fac.ex:977-985); `complete_charge_3ds` (fac.ex:582) resolves the AUTHORITATIVE callback result (`resolve_callback_3ds`, fac.ex:696) and runs a **fail-closed Y+CAVV strength gate** (`gate_3ds_strength`, fac.ex:707-720) BEFORE settlement; `finalize_authenticated_charge` (fac.ex:732-785) handles authenticated / attempted→step_up / decline and **reverses weak-3DS captures** (`refund_quietly`, fac.ex:801-808); server-side settle via `store_3ds_result`/`bind_3ds`/`complete_from_callback` (fac.ex:608,634,656). All exposed: `charge_card`,`complete_3ds`,`checkout_intent`,`store_3ds_result`,`bind_3ds`,`complete_from_callback` (payment_link_controller.ex:46,117,139,75,89,104). Decline outcome surfaced as `{:risk_blocked, outcome}` → 402 (payment_link_controller.ex:30-33,146-149).
- session: HPP-redirect only. `generate_payment_link` → `create_invoice` (session_based_checkout.ex:142,782-818) hands back `redirect_data`/`spi_token` in the create response (checkout_session_controller.ex:253-261) and defers the challenge to PowerTranz's hosted page. There is **no complete-3ds endpoint, no strength gate, no step-up, no retry, no in-band challenge completion** on the session controller (checkout_session_controller.ex only has create/show/delete/simulate). The webhook handler `determine_payment_status` (session_based_checkout.ex:940-992) marks success purely on `hold/authorized/captured` stage with **zero 3DS validation**. The only session 3DS check that exists, `validate_3ds_for_session` (fac.ex:1386, checks `threeDS.isSuccessful=="Y"` — weaker than Y+CAVV), sits inside the DEAD `Fac.process_session_webhook` (fac.ex:1277) which nothing calls.
- gap: Session path has parity with the LEGACY HPP flow (challenge handled on PowerTranz's page) but NOT with the modern CDE reference: no server-side Y+CAVV strength gate, no reverse-on-weak-3DS, no step-up/retry surfacing, no complete-3ds. Note the order-BASED inbound webhook `[commerce-worker]` applies a 3DS strength validation before marking paid; the session-BASED inbound branch bypasses it (goes straight to `determine_payment_status`, which trusts the stage).
- severity: P1 (a weak/attempted 3DS that still returns hold/authorized is accepted and the order marked paid; the reference refunds+declines it)
- effort: M
- reuse: `gate_3ds_strength`, `finalize_authenticated_charge`, `resolve_callback_3ds`, `store_3ds_result`/`complete_from_callback` (fac.ex:696-808) — route session completion through `complete_charge_3ds` instead of trusting the webhook stage; or add a strength check in `determine_payment_status`.

### 2. Auth vs capture (FAC auth and capture are separate PowerTranz txns)
- order-first: Records the TRUE stage and keeps auth≠capture. Legacy HPP webhook calls `hold_funds` (auth) then updates status (fac.ex:307-334, hold_funds 425-430); stage mapping sale/capture/collect→"captured", auth/hpp_response→"authorized" `[commerce-worker webhook_processor.ex:256-261]`; a `CaptureFlipReconciler` flips authorized→captured only once the FAC settlement report confirms capture `[commerce-worker, out-of-repo]`. CDE purchase is a sale then `settle_authenticated` marks paid (fac.ex:787-797); store-mode is auth-then-void.
- session: Collapses everything to captured. `determine_payment_status` treats `hold == true` (a pre-auth) AND `authorized` as success (session_based_checkout.ex:952,958,960), then `create_transaction_record` HARD-CODES `status: transaction_captured` (session_based_checkout.ex:1239) regardless of the real stage, and `mark_order_as_paid` marks the order paid (session_based_checkout.ex:1289-1319). No `/fac/capture` call is ever made — `mark_order_as_paid` only does a LOCAL `update_transaction_status(..., "captured")` (session_based_checkout.ex:1296), which just relabels the row it created.
- gap: An authorize-only / hold (funds NOT settled) is written as `captured` and the order marked paid, and no capture step or settlement-driven flip ever runs. The reference either records "authorized" and lets the reconciler flip it, or performs an explicit capture; the session path does neither.
- severity: P0 (order shows paid + txn shows captured while funds may only be authorized/held; no capture is ever triggered)
- effort: M
- reuse: `CommercePayments.capture/2` (commerce_payments.ex:64) and `Fac.capture_funds` (fac.ex:431); the stage-mapping + CaptureFlip pattern from `[commerce-worker webhook_processor.ex:256-277]` — write the transaction with the webhook's real stage and let the FAC reconciler own the flip, instead of hard-coding `transaction_captured`.

### 3. Refunds / voids
- order-first: No merchant-facing order-refund endpoint either (only Shopify's `refund_session`, shopify_controller.ex:44, and disputes). But the CDE flow auto-reverses via `refund_quietly` → `CommercePayments.refund(txn)` (fac.ex:803-804), and provider primitives exist: `CommercePayments.refund/void/capture` (commerce_payments.ex:75-88), `Fac.refund_funds/void_funds` (fac.ex:437-448). All key off the provider transaction id.
- session: No refund/void code anywhere in the session modules; `SessionBasedCheckout` and `checkout_session_controller` expose none. A session order's `ledger_transactions` row is created with `payment_method_order_id => payment_data[:transaction_id]` (session_based_checkout.ex:1238), so the SAME primitives could refund/void it — provided that stored id is the real PowerTranz transaction GUID (see gap).
- gap: Machinery is shared (both refund/void through the transaction's `payment_method_order_id`), so there is no session-specific *machinery* gap — the shared gap is that NEITHER checkout path has a merchant refund/void API in commerce-api. The session-specific RISK is identifier provenance: the session path stores the webhook's `transaction_id` verbatim; if that is the combined `O.x.S.x` reference rather than the PowerTranz GUID, `CommercePayments.refund/void` (which POST `/v1/payments/:id/...`) will not resolve it.
- severity: P2 (parity gap is shared; session-specific exposure is the unverified identifier)
- effort: S
- reuse: `CommercePayments.refund/void` (commerce_payments.ex:75-88); first ensure the session transaction persists the PowerTranz txn id as `payment_method_order_id` the way `log_payment_method_id` does for order-first (utils.ex:57-60).

### 4. Saved cards / tokenization / card-on-file
- order-first: Yes. Tokenized-card charge via opaque `card_ref` (`charge_by_ref`, commerce_payments.ex:35; `charge_card_ref`, fac.ex:957-974); card-on-file **vaulting** via `mode: "store"` — `checkout_intent(...,"store")` uses a small `store_verify_amount` hold (fac.ex:889-911) and `settle_authenticated` store-branch voids the hold and returns a `pan_token` (fac.ex:789-792); recurring via `subscription_token` (fac.ex:214-252).
- session: Recurring-token only. `create_checkout_session` accepts `subscription_token`/`billing_plan_id` and threads `is_recurring`/`subscription_token` into the payment link (session_based_checkout.ex:127,741-743,792-793). There is NO `card_ref` charge, NO store-mode/`pan_token` vaulting, NO `mode` parameter — a session cannot create a saved card or charge a stored one; it can only ride a PRE-EXISTING subscription token.
- gap: Session path cannot vault a card (card-on-file "store" flow) and cannot charge a saved `card_ref`; it only supports recurring against a token minted elsewhere.
- severity: P1 (functional gap — no saved-card capture or reuse for sessions)
- effort: L (session flow is HPP-redirect; adding saved cards means adopting the CDE `charge_by_ref` + store-mode path)
- reuse: `checkout_intent`/`generate_charge`/`complete_charge_3ds` store-mode + `charge_by_ref` (fac.ex:878,563,582,957; commerce_payments.ex:35) — the same CDE surface the order-first path already ships.

### 5. FAC settlement reconciliation (rpTransaction / CaptureFlipReconciler / mix payments.reconcile*)
- order-first: Reconciled. The reconciler + `mix payments.reconcile_fac` matching FAC rpTransaction settlement records live `[commerce-worker, out-of-repo]`; they key on `ledger_transactions.payment_method_order_id`, which the order-first path sets to the real PowerTranz txn id via `log_payment_method_id` (utils.ex:57-60) during the webhook/charge, and records the true auth/capture stage so the authorized→captured flip has something to flip.
- session: Partially. `create_order_from_session` writes a `ledger_transactions` row and `enqueue_transaction_entries` → `Api.Workers.Migrators.Final.TransactionEntries` on `:transaction_entry_migration` (session_based_checkout.ex:1470-1511) — note the in-file history that this was a `Logger.info` stub, so captures landed a ledger row with NO entries until back-filled (session_based_checkout.ex:1455-1469). Reconciliation itself is `[commerce-worker, out-of-repo]`; within commerce-api the session path produces the terminal artifacts, but (a) it stores the webhook `transaction_id` as `payment_method_order_id` (provenance unverified vs PowerTranz GUID, session_based_checkout.ex:1238) and (b) it writes `captured` immediately (session_based_checkout.ex:1239), so the CaptureFlip authorized→captured correction is bypassed.
- gap: If the stored `payment_method_order_id` is not the PowerTranz settlement GUID, the reconciler cannot match a session transaction to the rpTransaction report → session captures fall outside settlement reconciliation; and because the row is eagerly `captured`, a genuinely authorized-but-unsettled session txn is permanently mislabeled with no reconciler correction.
- severity: P1 (settlement matching depends on an unverified identifier; eager-captured rows are invisible to the CaptureFlip reconciler)
- effort: M
- reuse: `log_payment_method_id` (utils.ex:57-60) to persist the true PowerTranz id; adopt the order-first stage-recording so `[commerce-worker]` CaptureFlipReconciler / `mix payments.reconcile_fac` can match and flip.

## DONE

Top gaps:
- **P0 — Auth/capture collapsed to "captured" (dimension 2):** the session path treats a `hold`/pre-auth as success, hard-codes the transaction to `transaction_captured` (session_based_checkout.ex:1239,952-961), marks the order paid, and never calls `/fac/capture` — so an order can read "paid" while funds are only authorized, with no capture or settlement-driven flip.
- **P1 — No modern 3DS strength gate for sessions (dimension 1):** the reference runs a fail-closed Y+CAVV gate with reverse-on-weak (`gate_3ds_strength`/`finalize_authenticated_charge`, fac.ex:707-785); the session webhook accepts any hold/authorized/captured stage with no 3DS validation (session_based_checkout.ex:940-992).
- **P1 — Saved cards + settlement identifier (dimensions 4 & 5):** sessions cannot vault or charge a saved `card_ref` (order-first store-mode/`pan_token` at fac.ex:789-792,957-974), and they persist the webhook `transaction_id` verbatim as `payment_method_order_id` (session_based_checkout.ex:1238) — unverified against the PowerTranz GUID that refunds (dim 3) and FAC settlement reconciliation (dim 5) both key on.
